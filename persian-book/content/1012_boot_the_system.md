## فرآیند بوت
درک آن بسیار مهم است زیرا در این مرحله کنترل بسیار کمی روی سیستم دارید و نمی توانید دستورات زیادی برای عیب یابی صادر کنید. شما باید درک خوبی از آنچه در حال وقوع است داشته باشید.

1. سیستم عامل مادربرد یک تست PowerOnSelfTest (POST) انجام می دهد.
2. مادربرد بوت‌لودر (Bootloader) را بارگذاری می کند
3. بوت‌لودر (Bootloader) کرنل/هسته لینوکس را بر اساس تنظیمات/فرمان های آن بارگذاری می کند
4. Kernel سیستم (سیستم‌فایل (Filesystem) ریشه) را بارگیری و آماده می کند و برنامه اولیه سازی را اجرا می کند.
5. برنامه Init سرویسی مانند وب سرور، رابط گرافیکی، شبکه و ... را راه اندازی می کند.

همانطور که در بخش قبلی (101.1) بحث کردیم، سیستم عامل روی مادربرد می تواند BIOS یا UEFI باشد. 

### بایوس
سیستم خروجی ورودی پایه

- مسن تر
- محدود به یک بخش از دیسک و نیاز به یک بوت‌لودر (Bootloader) چند مرحله ای دارد
- می تواند بوت‌لودر (Bootloader) را از هارد داخلی/خارجی، CD/DVD، درایو فلش USB، سرور شبکه راه اندازی کند.
- در صورت بوت شدن از هارد دیسک، ضبط اصلی بوت استفاده خواهد شد (1 بخش)

### UEFI
رابط سفت‌افزار یکپارچه قابل توسعه 

- مدرن و فانتزی
- یک پارتیشن (Partition) دیسک ویژه برای بوت‌لودر (Bootloader) مشخص می کند. پارتیشن (Partition) سیستم EFI (ESP) نامیده می شود
- ESP FAT است و روی `/boot/efi` نصب شده است و فایل های بوت‌لودر (Bootloader) دارای پسوند `.efi` هستند

> می توانید `/sys/firmware/efi` را بررسی کنید تا ببینید آیا از سیستم UEFI استفاده می کنید یا خیر

### بوت‌لودر (Bootloader)
بوت‌لودر (Bootloader) حداقل سخت افزار مورد نیاز برای بوت شدن سیستم را مقداردهی اولیه می کند. سپس، سیستم عامل را پیدا کرده و اجرا می کند.

از نظر فنی می‌توانید به UEFI خود اشاره کنید تا هر چیزی را که می‌خواهید اجرا کند، اما معمولاً در سیستم‌های گنو/لینوکس، ما از GRUB استفاده می‌کنیم. GRUB را می توان برای اجرای هر برنامه خاصی که نیاز دارید استفاده کرد اما به طور کلی سیستم عامل را اجرا می کند. 

### هسته(kernel)

هسته(kernel) هسته سیستم عامل شما است. اساسا خود لینوکس است. بوت‌لودر (Bootloader) شما هسته را در حافظه بارگذاری می کند و آن را اجرا می کند. اما هسته برای شروع به اطلاعات اولیه نیاز دارد. چیزهایی مانند درایورهایی که برای کار با سخت افزار ضروری هستند. این موارد در `initrd` یا `initramfs` در کنار هسته ذخیره می شوند و در طول بوت استفاده می شوند.

همچنین می توانید پارامترها را در حین بوت با استفاده از تنظیمات Grub به هسته ارسال کنید. به عنوان مثال، ارسال 1 یا S منجر به بوت شدن سیستم در حالت تک کاربره (بازیابی) می شود. یا می توانید با ارسال `vga=792` به هسته در هنگام بوت، گرافیک خود را مجبور کنید در حالت 1024×768x24 کار کند.

#### dmesg

لینوکس گزارش های فرآیند بوت را در طول بوت به شما نشان می دهد. برخی از سیستم‌های دسکتاپ این را در پشت یک صفحه نمایش شیک پنهان می‌کنند که می‌توانید با استفاده از کلید `Esc` پنهان کنید یا `Ctrl+Alt+F1` را فشار دهید.

به دلایل متعددی که خارج از محدوده این دوره است، هسته لاگ های خود را در "Kernel Ring Buffer" ذخیره می کند. پس از کامپایل شدن فرآیند بوت، دیمون syslog * گزارش های بوت* را جمع آوری کرده و در `/var/log/dmesg` ذخیره می کند.

برای مشاهده همه گزارش‌ها از جمله آنچه که پس از فرآیند بوت ثبت شده است، از دستور `dmesg` استفاده می‌کنیم.

همچنین می‌توانیم از `journalctl -k` برای بررسی گزارش‌های هسته استفاده کنیم یا از `journalctl -b` برای بررسی گزارش‌های راه‌اندازی استفاده کنیم (یا حتی از `journalctl -u kernel` برای دیدن همه گزارش‌های قبلی نیز استفاده کنیم).

علاوه بر اینها، اکثر سیستم‌ها گزارش‌های بوت را در یک فایل متنی نیز نگه می‌دارند و می‌توان آنها را به ترتیب در `/var/log/boot` یا `/var/log/boot.log` در سیستم‌های مبتنی بر Debian یا Red-Hat یافت.

#### /var/log/messages

پس از بالا آمدن فرآیند init، syslog daemon پیام‌ها را ثبت می‌کند. دارای مهر زمانی است و در طول راه اندازی مجدد باقی خواهد ماند.

* هسته همچنان در حال ثبت پیام های خود در هسته بافر رینگ است
* در برخی از سیستم ها، ممکن است `/var/log/syslog` نامیده شود
* بسیاری از گزارش های دیگر در `/var/log` وجود دارد

## init

هنگامی که مقداردهی اولیه هسته به پایان رسید، زمان شروع برنامه های دیگر است. برای انجام این کار، کرنل فرآیند Initialization Daemon را اجرا می کند و از راه اندازی دیمون ها، سرویس ها، زیرسیستم ها و برنامه های دیگر مراقبت می کند. با استفاده از سیستم init می توان گفت "من به سرویس A و سپس سرویس B نیاز دارم. سپس به C و D و E نیاز دارم اما D را شروع نمی کنم مگر اینکه A و B در حال اجرا باشند". ادمین سیستم می تواند از سیستم init برای توقف و شروع خدمات بعدا استفاده کند.

سیستم های init مختلفی وجود دارد:

- **SysVinit** مبتنی بر Unix System V است. دیگر زیاد مورد استفاده قرار نمی گیرد اما مردم آن را دوست داشتند زیرا از فلسفه های یونیکس پیروی می کرد. ممکن است آن را در دستگاه های قدیمی تر یا حتی در دستگاه هایی که اخیراً نصب شده اند مشاهده کنید.
- **upstart** جایگزینی مبتنی بر رویداد برای دیمون init سنتی بود که توسط Canonical (افراد پشت اوبونتو) توسعه یافت. هدف این پروژه ساخت جایگزینی برای SysV بود که در سال 2007 منتشر شد. در نهایت، این پروژه به دلیل پذیرش گسترده Systemd متوقف شد. حتی اوبونتو این روزها از Systemd استفاده می کند، اما هنوز هم می توان نسخه جدید را در ChromeOS گوگل پیدا کرد.
- **Systemd** جایگزین جدید است. نخبه گرایان لینوکس به دلیل پیروی نکردن از اصول یونیکس از آن متنفرند، اما به طور گسترده توسط توزیع کنندگان بزرگ پذیرفته شده است. می تواند خدمات را به صورت موازی شروع کند و کارهای فانتزی زیادی انجام دهد! 

فرآیند init دارای شناسه 1 بود و با اجرای آن می توانید آن را پیدا کنید 

```
# which init
/sbin/init
# readlink -f /sbin/init
/usr/lib/systemd/systemd
# ps -p 1
PID TTY TIME     CMD
1   ?   00:00:06 systemd
```
 
با استفاده از دستور `pstree` می توانید سلسله مراتب فرآیندها را بررسی کنید.

```text
pstree
```

## systemd
جدید، محبوب و منفور است. بسیاری از ایده‌های جدید، اما از برخی از اصول محبوب یونیکس پیروی نمی‌کنند (مثلاً: ذخیره نشدن گزارش‌ها در یک فایل متنی یا تلاش زیاد برای کمک به شما، اما درخواست رمز عبور ریشه زمانی که دستورات sudo را اجرا نمی‌کنید). این به ما امکان می دهد در صورت اتصال سخت افزار، در فواصل زمانی، در صورت راه اندازی سرویس دیگری، سرویس ها را اجرا کنیم و ...

systemd حول **واحد** ساخته شده است. یک واحد می تواند یک سرویس، گروهی از خدمات یا یک عمل باشد. واحدها دارای یک نام، یک نوع و یک فایل پیکربندی هستند. 12 نوع واحد وجود دارد: خودکار، دستگاه، مانت، مسیر، محدوده، سرویس، برش، عکس فوری، سوکت، تعویض، هدف و تایمر.

ما از `systemctl` برای کار با این واحدها و `journalctl` برای دیدن گزارش ها استفاده می کنیم.

```
# systemctl list-units
# systemctl list-units --type=target
# systemctl get-default # default target (groups of services are started via target unit files)
```

واحدها را می‌توانید در این مکان‌ها پیدا کنید (به ترتیب اولویت):

1. `/etc/systemd/system/`
2. `/run/systemd/system/`
3. `/usr/lib/systemd/system`

```
# systemctl list-unit-files
# systemctl cat ntpd.service
# systemctl cat graphical.target
```

ما می توانیم از این دستورات برای کار با سرویس ها استفاده کنیم:

```
# systemctl stop sshd
# systemctl start sshd
# systemctl status sshd
# systemctl is-active sshd
# systemctl is-failed sshd
# systemctl restart sshd
# systemctl reload sshd # re-reads the configuration of the service configs
# systemctl daemon-reload sshd # re-reads the configuration of the systemd configs of this service
# systemctl enable sshd
# systemctl disable sshd
```

دستورات دیگری نیز وجود دارد:

```
# systemctl is-system-running # running, degraded, maintenance, initializing, starting, stopping
# systemctl --failed
```

برای بررسی گزارش‌ها، باید از ابزار `journalctl` استفاده کنیم:

```
# journalctl # show all journal
# journalctl --no-pager # do not use less
# journalctl -n 10 # only 10 lines
# journalctl -S -1d # last 1 day
# journalctl -xe # last few logs
# journalctl -u ntp # only ntp unit
# journalctl _PID=1234
```

## SysV
سیستم init قدیمی است. هنوز هم می توان در بسیاری از سیستم ها استفاده کرد. فایل‌های کنترل در `/etc/init.d/` قرار دارند و به اسکریپت‌های bash عمومی نزدیک‌تر هستند. در بسیاری از موارد می توانید مانند:

```
/etc/init.d/ntpd status
/etc/init.d/ntpd stop
/etc/init.d/ntpd start
/etc/init.d/ntpd restart
```
